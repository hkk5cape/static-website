1. Python Requests

Requests is a third-party Python library for communicating with web servers over HTTP or HTTPS. A program can use it to retrieve a product catalogue, submit form data or exchange data with an API. It is installed with pip and imported as requests. [1]

A request specifies a URL and an HTTP method. requests.get() retrieves a representation, while requests.post() submits data for processing. The params argument supplies query parameters; json supplies a JSON request body. The returned Response contains the status code, headers and response body. Its json() method decodes a JSON response into Python values. [1, 2]

Reliable code sets a timeout, calls raise_for_status() to detect HTTP errors, and handles connection problems and invalid JSON. Successfully decoding JSON does not prove the request succeeded. Requests timeouts control connection and read waiting; they are not an overall download deadline. [1, 2]

2. JSON and XML data formats

Both formats let programs represent structured information as text. The following examples describe the same product. The price is deliberately a string so the application can interpret it as an exact decimal amount rather than relying on binary floating-point arithmetic.

JSON example:
{"id": 1, "name": "Notebook", "price": "25.50", "currency": "ZAR"}

XML example:
<product><id>1</id><name>Notebook</name><price currency="ZAR">25.50</price></product>

2.1 JSON: meaning and uses

JSON means JavaScript Object Notation. It represents data using objects, arrays, strings, numbers, Boolean values and null. It is independent of JavaScript and can be exchanged between programs written in different languages. A shop could use it to transfer product records between a server and a mobile app. [3]

Advantages:
1. Compact syntax: it avoids repeated opening and closing tags for each value.
2. Simple structures: objects and arrays are convenient for records and lists.
3. Language independence: separate systems can share the same text format.
4. Nested values: a product can contain related lists or objects. [3]

Disadvantages:
1. No standard comment syntax: explanatory comments cannot be embedded in ordinary JSON.
2. No native date type: applications must agree how dates are represented.
3. Numeric interoperability limits: different implementations may handle very large or precise numbers differently.
4. Duplicate object names are troublesome: receivers may reject them or interpret them differently, so producers should avoid them. [3]

2.2 XML: meaning and uses

XML means Extensible Markup Language. It uses named elements, attributes and nested content. It can represent a document containing text and markup, or structured records such as a supplier product feed. Unlike HTML, its tags can be designed for the application's data. [4]

Advantages:
1. Descriptive tags: element names make the structure explicit.
2. Mixed content: text and nested markup can coexist, which helps document-oriented applications.
3. Validation options: an XSD schema can define permitted structures and types.
4. Reusable schemas: shared definitions help multiple organisations agree a data contract. [4, 5]

Disadvantages:
1. Verbosity: repeated tags can make a simple record longer than an equivalent JSON record.
2. Structural complexity: developers must choose how to divide information between elements and attributes.
3. Schema maintenance: strict contracts require coordination when structures change.
4. Parsing risks: untrusted XML requires appropriate parser configuration and protections against malicious input. [4–6]

For a simple catalogue API, JSON is a practical choice. XML may be preferable when an integration already requires a specific XML schema. These are design judgements; neither format is always faster or better.

3. RESTful APIs

An API defines how software components interact. REST, or Representational State Transfer, is an architectural style for distributed systems. A RESTful API exposes resources through a consistent interface and exchanges representations of those resources. JSON is one possible representation format; REST does not require it. [7]

REST separates client and server, keeps requests self-contained, defines cache behaviour, and allows layered systems. Its uniform interface includes resource identification, representation-based interaction, self-descriptive messages and links that guide available actions. Code supplied for client execution is optional. Statelessness does not prohibit a server from storing products or orders; it means a request should not depend on remembered conversational context. [7]

For an HTTP example, a client requests GET /products/1. The server checks access, obtains the resource and responds with a representation and status code. POST /orders can submit an order for processing. PUT requests replacement of a resource's state; DELETE requests removal of its association with its URI. A 200 response indicates success; 201 indicates creation; 404 indicates the target was not found. [8]

Such APIs can connect a shop website, mobile app and supplier system to shared services. The example routes are illustrative and are not endpoints in the earlier Django application.

3.1 RESTful API advantages

1. Separation of concerns: clients and servers can develop independently while respecting their interface.
2. Scalability: self-contained requests reduce dependence on a particular server's conversational state.
3. Cache support: suitable responses can be reused, reducing repeated work.
4. Interoperability: standard representations and HTTP semantics help different platforms communicate. [7, 8]

3.2 RESTful API disadvantages

1. Additional message data: self-contained requests may repeat information across calls.
2. General-interface overhead: a uniform interface can be less efficient than one tailored to a specific interaction. [7]
3. Network failure handling: clients must distinguish failed operations from missing responses and avoid unsafe retries of non-idempotent requests. [8]
4. Contract coordination: changing representations or resource behaviour can disrupt clients; compatibility needs deliberate management. This is a practical integration concern, not a defect unique to REST.
